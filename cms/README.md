# cms/

The Rails 8.1 application of the project: it stores the pages, their draft
and versions, publishes them, keeps the media library, the site style and
the site's header and footer (parts kept and published as pages are),
answers the editor through a JSON API under `/api`,
and serves the pages a
visitor sees, rendered on the server in the approved design's theme
(`../design/`) and cached in the browser and in Solid Cache (see "How the
pages are cached"). Its jobs (a publish set for a time, the pruning of
old versions, the purge of unused images) run in Solid Queue, inside the
server (see "The jobs").

Run the commands from this folder. They are written `ruby bin/rails ...`
because Windows cannot start an extensionless script by itself; on Linux
and macOS `bin/rails ...` works as well.

## Installing the gems

The gems go into `vendor/bundle`, inside this folder, never into the
system:

```
bundle config set --local path vendor/bundle
bundle install
```

On Windows with RubyInstaller, Bundler writes the gems' launchers into the
user's `AppData/Local/Microsoft/WindowsApps` folder unless told otherwise.
Point it inside `vendor/bundle` before installing, in PowerShell:

```
$env:BUNDLE_SYSTEM_BINDIR = "$PWD/vendor/bundle/ruby/3.4.0/bin"
```

or in a POSIX shell, on the same line as the install:

```
BUNDLE_SYSTEM_BINDIR="$PWD/vendor/bundle/ruby/3.4.0/bin" bundle install
```

`json` is pinned at 3.0.2 or later on purpose: from 3.0 the parser refuses
a member name repeated in one object, which the API answers with a 422;
under 2.x the same option is silently ignored and the last value wins.
There is no `image_processing` and no libvips: the editor resizes images in
the browser before uploading them, and the server makes no variants
(`config.active_storage.variant_processor = :disabled`).

`bundle clean`, run with the same `BUNDLE_SYSTEM_BINDIR`, removes from
`vendor/bundle` the gems the lockfile no longer names. On 1 October 2026
it removed `image_processing`, `mini_magick`, `ruby-vips` and `ffi`, left
from before libvips was dropped (129 MB to 127 MB); `bundle check` was
satisfied afterwards, the suite passed, and the listing of
`AppData/Local/Microsoft/WindowsApps` was the same before and after.

If you have run `bundle install` before on a RubyInstaller installed for
all users, without pointing Bundler elsewhere, its launchers may be in
`AppData/Local/Microsoft/WindowsApps`: each is a file without an extension
whose third line is `# This file was generated by RubyGems.`, with a `.bat`
of the same name beside it that runs `@ruby.exe "%~dpn0" %*`. In
PowerShell, this lists them and nothing else:

```
Get-ChildItem "$env:LOCALAPPDATA\Microsoft\WindowsApps" -File | Where-Object { (Get-Content $_.FullName -TotalCount 3 -ErrorAction SilentlyContinue) -contains '# This file was generated by RubyGems.' }
```

Delete those, and the `.bat` of each. On 2 October 2026 the same filter
listed 23 of the 46 files in `vendor/bundle/ruby/3.4.0/bin`, the ones
without an extension, and 0 of the 17 in that machine's WindowsApps.

## Running it

```
ruby bin/rails db:prepare
ruby bin/rails db:seed
ruby bin/rails server
```

`http://127.0.0.1:3900/up` answers 200 when the app is up. The server
listens on 127.0.0.1 only, port 3900, the project's own (3000 is every
project's): the API has no authentication. That is not left to the command
line. `bin/rails` makes 127.0.0.1 and 3900 the defaults of `rails server`,
which would otherwise listen on 0.0.0.0:3000 in production;
`config/puma.rb` does the same for `puma` started by itself; and a Puma
plugin there stops the boot, before any socket is opened, when the server
is asked to listen anywhere else (`-b 0.0.0.0`, `BINDING`, a bind line, a
host name). `-p` changes the port. `ruby bin/dev` starts the same server.
[test/config/puma_binding_test.rb](test/config/puma_binding_test.rb) builds
Puma's configuration from the file as Puma does and starts its plugins as
Puma's launcher does. On 2 October 2026, `ruby bin/rails server` with no
option printed `Listening on http://127.0.0.1:3900`, and netstat showed
that one listener.

`db:seed` loads the example site, Slack Water, an invented open-water
swimming club, from [`../example-site/`](../example-site/), the one copy
of its pages and pictures, which the editor's browser demo reads too
([db/seeds/example_site.rb](db/seeds/example_site.rb)):
- the home page, the course a beginner swims out to the buoy line, at
  `http://127.0.0.1:3900/`;
- a content page, `/winter-series`;
- a page that breaks assumptions on purpose, `/notices`: four columns, a
  word too long for any line, emoji and right-to-left text, nested lists, a
  long alt text, a dark band, a heading hidden on phones.

The fifteen images go into the media library as an upload does (a blob on the

read and checked before anything is uploaded or saved. Last, it

To start again from a new database, with the server stopped:

```
ruby bin/rails db:drop
ruby bin/rails db:prepare
```

`db:drop` deletes the development and test databases; `db:prepare`
creates development's three (the pages, the cache and the queue, as in
production), loads their schemas and, on a primary database it has just
created, runs the seed, the example site's or, with `EMPTY_SITE=1`, the
empty one (`ruby bin/rails db:reset` does both in one).
The images the old database pointed at stay in `storage/`, in its
two-character folders, as files no row names any more (the fifteen seed
images, 248 KB, per seed run); delete those folders too for a clean disk.

On Windows `db:drop` used to fail with `Permission denied @ apply2files -
.../storage/development.sqlite3` even with nothing else running: its
environment check opens the database and keeps the connection, and
Windows does not delete an open file. [lib/tasks/release_connections.rake](lib/tasks/release_connections.rake)
closes every connection first. `test/lib/tasks/db_drop_test.rb` runs
`db:create db:schema:load`, then `db:drop`, in processes of their own on a
database of their own; with the rake file moved away it failed with that
error, and with it in place it passed, as did `db:drop` and `db:reset` on
the development database (1 October 2026). A server still running holds
the file the same way: stop it first.

A first look at the API, with the CMS running (`npm start` from the
repository's root). The four steps make a page, list the pages, publish
the page just made, and read the site's style. In a POSIX shell (Git
Bash on Windows, where `curl` is the real one):

```sh
page=$(curl -s -X POST http://127.0.0.1:3900/api/pages -H "Content-Type: application/json" -d '{"title":"Winter series","slug":"winter"}')
echo "$page"
id=$(echo "$page" | grep -o '"id":[0-9]*' | head -1 | cut -d: -f2)
curl -s http://127.0.0.1:3900/api/pages
curl -s -X POST http://127.0.0.1:3900/api/pages/$id/publish -H "Content-Type: application/json"
curl -s http://127.0.0.1:3900/api/site-style
```

In Windows PowerShell, where `curl` is another command, the same four
steps with `Invoke-RestMethod`:

```powershell
$page = Invoke-RestMethod -Method Post -Uri http://127.0.0.1:3900/api/pages -ContentType application/json -Body '{"title":"Winter series","slug":"winter"}'
$page
Invoke-RestMethod http://127.0.0.1:3900/api/pages
Invoke-RestMethod -Method Post -Uri "http://127.0.0.1:3900/api/pages/$($page.page.id)/publish" -ContentType application/json -Body '{}'
Invoke-RestMethod http://127.0.0.1:3900/api/site-style
```

The first answer begins `{"page":{"id":4,...`: the id is the new page's,
whatever the database held (the seeded one has three pages), and the
publish is of that page and no other. The address `winter` is taken once
the first step has run, so a second run is refused with a 422 at `/slug`:
change the address in the first step to run it again.

Every POST, PUT and PATCH says `Content-Type: application/json`, even
with no body, as the publish above does; without it the answer is 415
(see "Writes from other sites" below).

`builder/test/readme-curl.rails.test.ts` runs both blocks as they are
written, with only the address of the CMS changed to the one the test
run starts, and checks each answer's status and that the page published
is the one the first step made.

## Testing it

In two commands:

```
ruby bin/rails db:test:prepare
ruby bin/rails test
```

The single form `ruby bin/rails db:test:prepare test` works as well, with
one condition. railties 8.1.4 runs the second task by spawning `rails`
(`test_unit/runner.rb`), found on the PATH, and Bundler puts
`vendor/bundle/ruby/3.4.0/bin`, where the install above writes the gems'
launchers, `rails.bat` among them, first on it, so it is found even with
no `rails` on the machine's own PATH. On 2 October 2026, with no `rails`

--version`; with that folder's `rails` and `rails.bat` moved away, the

## The pages a visitor sees

| Address | What it serves |
| --- | --- |
| `/` | the page marked as home (`PATCH /api/pages/:id {home: true}`), its last published version; the 404 page while there is none |
| `/<slug>` | any other published page; an address it had before answers 301 to where it is now, and the home page's own slug answers 301 to `/` |
| `/preview/<page id>` | the page's draft, through the same layout and partials, with `Cache-Control: no-store`, `X-Robots-Tag: noindex` and a robots meta tag |
| anything else shaped like a slug | the 404 page, a document of its own rendered in the site's look, with status 404 |
| `POST /`, `POST /<slug>` | a form of that page, sent by a visitor ([Forms a visitor sends](#forms-a-visitor-sends)) |
| `/sent/<form id>`, `/<slug>/sent/<form id>` | what the form says once its answers are kept, after the 303; `no-store` and `noindex` |
| `POST /preview/<page id>` | a form sent from the draft preview: 403, a page saying forms are sent from the published page, and nothing kept |

- **One partial per block type** in [app/views/blocks/](app/views/blocks/),
  fifteen in all, walked by `BlocksHelper#render_document`. Every block
  root carries `data-block-id` and `data-block-type`, and `data-style`
  repeats the stored style for the contract with the editor's renderer.
- **Style is by class.** [BlockStyle](app/models/block_style.rb) turns each
  token of a block's style into a class of
  `app/assets/stylesheets/tokens.css` (`spaceInside: "l"` is `pad-l`, the
  same on tablets only is `tablet-pad-l`), and only for values the
  schema's enums list. `tokens.css` is generated from `schema/tokens.json`
  by `ruby bin/rails tokens:css`; `site.css` is the design's `theme.css`,
  with the same class names and the same container queries on the page
  root. The site style's tones, type scale and letter width reach the
  page as data attributes on `.site`, which the generated rules read. A section's
  `columnWidths` (`3:2` is `widths-3-2`, on desktop only), an image's crop
  (`aspect: "16:9"` is `aspect-16-9`) and a section's `spaceAbove` and
  `spaceBelow` (`space-above-section-s`, `phone-space-below-xxl`) are
  classes of the same file.
- **Colours that read on every band.** A background class also sets the
  colours of what sits on it: paper text, headings, links and icons on the
  dark slots (Text, Primary, Muted), ink on Accent, the theme's own on the
  other light slots, and those of the band behind for `none`, so a light
  column inside a dark band, or a phone override to `none`, never keeps
  paper text on paper. The focus ring, 3 px and 3 px outside what has
  focus, is ink on light bands and paper on dark ones: the background
  class sets `--ring-color` for the elements inside it, not for itself,
  because a button with a dark background of its own draws its ring on
  the band around it.
- **No script, no inline style.** The pages carry a static
  Content-Security-Policy, `script-src 'none'`, frames only from the video
  and map providers, and no nonce: Rails' nonce reads the session, and a
  session writes a cookie onto a page meant to be cached. The layout has
  no `csrf_meta_tags` and no `csp_meta_tag`.
- **Video and map load on click, without script**: a lazy iframe inside a
  closed `details`. `node tools/probes/lazy-iframe-in-details.ts`, from the
  repository root, showed on Chromium 151 that such a frame is not
  requested until the details opens, even 3000 px from the viewport where
  a lazy frame without details is fetched at once. The closed card is
  drawn in CSS, so nothing reaches the provider before the click. Other
  browsers were not tried.
- **Rich text** ([RichTextHelper](app/helpers/rich_text_helper.rb)) is
  built with `tag`, `content_tag` and `safe_join`, so it is a SafeBuffer
  and the author's text is always escaped; there is no `raw` and no
  `html_safe` on what an author typed. Addresses go through
  [RenderPolicy](app/models/render_policy.rb), a small pure module whose
  TypeScript twin is the editor's `../builder/src/render/policy.ts`, held
  to it by a test that runs both on the same values: a refused address is
  dropped and its text kept; a player or map address is built from
  provider and id, or coordinates.
- **Library images** are served through Active Storage's proxy route, on
  the page's own origin, with their width, height and alt text.
- **Icon box icons** are drawn inline from `../schema/icons.svg`, rebuilt
  element by element with tag helpers; loading refuses anything but plain
  shapes.
- **The header and footer** are the site's parts
  ([app/models/site_parts.rb](app/models/site_parts.rb)): documents made of
  sections, columns and blocks as a page is, kept as pages of their own
  kind with a draft, versions and a publish, and drawn around every page
  in `<header>` and `<footer>` with the page's own partials. A page
  draws each part's published version, or, until the part publishes, its
  starter, [config/parts/header.json](config/parts/header.json) and
  [footer.json](config/parts/footer.json): the design's header (a logo, a
  menu that folds into Menu, the Join button, on one row on every device)
  and footer. The starters are checked as the CMS starts against the
  rules a part's draft is held to (a test starts the CMS in a process of
  its own with a starter broken, and it stops, naming the value); a
  part's draft holds no form and no anchor. A publish of a part
  reaches every published page at its next visit (see how the pages are
  cached, below); the preview draws the parts' drafts.

sideways scroll at 320. On a phone the header keeps one row, its section
never stacking: the logo, Menu and Join, Menu with its word where its
column has room for it (375 wide) and its icon alone where not (320).

## Forms a visitor sends

A form block is plain HTML with no script
([app/views/blocks/_form.html.erb](app/views/blocks/_form.html.erb)). It
posts to the page's own address: the block's id in `form`, each answer
under `answers[<field name>]` (a ticked box as `yes`), and `website`, a
field for robots that no person sees.
[SubmissionsController](app/controllers/submissions_controller.rb)
takes it.

**No CSRF token.** Rails keeps its token in the session, and a published
page is cached and shared: it has no session, carries no token and sets
no cookie. The controller says `skip_forgery_protection`, and on the
same route these take the token's place, each with a request test in
[test/integration/submissions_test.rb](test/integration/submissions_test.rb)
that fails when its guard is taken out:

| Guard | A form that breaks it gets |
| --- | --- |
| the `Origin` a browser sets on every form it posts must be this site's | 403, nothing read; the same with no `Origin`, or `null` |
| `rate_limit`: ten forms per address (the socket's peer, below) within ten minutes | 429 with `Retry-After: 600`; a form refused for its `Origin` (above) is never counted, the forms refused below count too |
| the field for robots is empty | a 303 to the confirmation as if kept, and nothing kept |
| only `application/x-www-form-urlencoded`, what a form without `enctype` sends | 415 |
| a body no larger than the largest form sends (below) | 413 |
| each answer within its field: required, one line where a line is asked, no control characters, the field's limit, an email's shape | 422, the page drawn again |
| what no browser sends from the form (no `form`, an answer that is not text, a box that is not `yes`) | 400 |
| a form id the published page no longer has | 409 |

**The count's store** is named for it, `config.x.submission_limit_store`
in `config/application.rb`, never left to the cache store: the tests'
`:null_store` counts nothing, so the limit could never fire there. It is
Solid Cache everywhere but in the tests, which count in memory and empty
it before each test. `npm run check:production` sends forms from one
address to a production boot, each naming another address in
`X-Forwarded-For`: one from the page, which gets 303; eleven from another
site, which get 403 each and are not counted; then ten more from the
page, which get nine 303s and, at the eleventh counted, a 429, counted in
Solid Cache. With the store set to `:null_store` the check fails.

**The address a form is counted under** is the socket's own peer
(`request.remote_addr`), set in `config.x.submission_limit_by` in
`config/application.rb` and read at every send. It is not Rails' default
for `rate_limit`, `request.remote_ip`: that takes `X-Forwarded-For` or
`Client-Ip` from any peer, not only a proxy's, so one header changed at
every send gave a form a count of its own, and one naming another
visitor's address used up that visitor's ten. A request test sends eleven
forms from one peer, each naming another address in one header or the
other, and the eleventh gets 429; with the limit keyed on `remote_ip` it
fails. The cost is that every visitor reaching the CMS through one
address shares one count: the CMS listens on `127.0.0.1` only
(`config/puma.rb`), so behind a front proxy on this machine every
visitor is `127.0.0.1`, and ten forms in ten minutes is the whole site's.
So the site's eleventh form in ten minutes is refused, whoever sends it,
and one client can use up the count for everyone: a program other than a
browser can name this site's `Origin`, and ten of its forms, kept or
refused for what they hold, give every visitor 429 for ten minutes. A
form refused for its `Origin` is refused before it is counted, so a page
of another site cannot do this through its visitors' browsers: a request
test sends eleven forms from one address, from another site or with no
`Origin`, which get 403 each; then ten of the address's own, kept with
303 or refused for what they hold with 422; and only the next gets 429.
A deployment that must count each visitor behind its proxy sets
`config.x.submission_limit_by` in its environment's file to read the
address the proxy names (`request.remote_ip`, with
`config.action_dispatch.trusted_proxies` set to an array holding the
proxy, which replaces Rails' default list), and its proxy must overwrite
`X-Forwarded-For` with the peer it saw and drop `Client-Ip`; as the CMS
listens on `127.0.0.1` only, the proxy is then the only process on the
way in that can name an address. A visitor is counted by the whole IPv6
address, so one with a whole prefix has many. Rails' check that
`Client-Ip` agrees with `X-Forwarded-For` is off
(`config.action_dispatch.ip_spoofing_check`): it raised wherever
`request.remote_ip` is read, Rails' own log line on every request
included, so one header added by any client gave a bare 500 at every
address. Nothing decides on `remote_ip` here. A request test and a
browser test send the two headers disagreeing to a page, its form and the
confirmation; with the check on, both get 500.

**The body's limit** is computed, not picked: every field of the largest
form the schema allows (20) at the longest limit (5000 characters), each
character four bytes of UTF-8 sent as `%XX` escapes (12 bytes), with one
character more, plus the names around them: 1,202,544 bytes. The largest
form at every field's limit and one character over sends 1,200,406
bytes, so a field over its own limit still gets its own message instead
of a 413; a test sends exactly that, and fails with the limit set lower.
A field's characters are counted as the schema counts them, code points,
after each CR LF the browser sends is made one line break, as the
browser counted it.

**Kept, refused.** A kept form is a row of `submissions`: the page, the
published version the form was read from, the form's id, a copy of its
fields in the schema's own shape, and the answers by field name, every
field included. So an answer still reads as it was sent after the form
changes in a later version. Then 303 to `<page address>/sent/<form id>`,
two or three path segments, which no page address can be. A refused form
is the page drawn again, `no-store`, never from the cache
(`render_blocks` raises if asked to cache a page drawn with a visitor's
answers), with what was written, each message under its field and tied
to it by `aria-describedby`, and the same list at the top as links to
the fields, since the form may sit far down the page. The log shows
`answers` as `[FILTERED]`. The editor reads and deletes the kept
answers through the API ("Responses" under "The API").

**From a cached page.** Nothing about a form depends on how the page was
served: a page the browser kept (304) or the CMS read whole from Solid
Cache posts the same way, and neither the post nor its refusal reads or
writes the page's cache. After a post, the browser drops what it kept of
that address (RFC 9111, section 4.4), so its next visit is a 200, read
whole from Solid Cache. `builder/e2e/submissions.spec.ts` shows it in
Chromium.

## How the pages are cached

A published page is cached at three levels, and nothing is ever deleted
to invalidate it: whatever changes a page's bytes changes a key, and
entries under old keys are never asked for again (Solid Cache drops them
as they age, two weeks by default, or as the cache fills, 256 MB in
[config/cache.yml](config/cache.yml)). The keys are made in
[PageCache](app/models/page_cache.rb).

- **In the browser.** `Cache-Control: max-age=0, public, must-revalidate`
  (Rails' order of the three directives), an ETag, and no
  `Last-Modified`, which a restored version published again would move
  back in time. Every visit asks again; a page that has not changed is a
  304 with no body, answered before the version's document is read, and a
  publish shows at the very next request. The ETag is a digest of the
  published version, the site style, the header's and footer's published
  versions (a part that has published nothing is named as its starter)
  and the release; `fresh_when` is not used, because its digest of the action's
  template sees neither the layout nor the partials a helper renders.
  The version is named by its id and by the moment the page was put
  live, to the microsecond, both on the page's row: ids start again
  whenever a database is made anew (`db:drop` then `db:prepare`, a backup
  restored), so a browser that held page 1, version 3 of the old database
  must not be told its copy is good for the new database's page 1,
  version 3.
- **The whole page in Solid Cache,** one entry per version, site style
  and parts' published versions, under the same name of the version: a visit
  after the first is one read, and a cache database that outlives the
  pages database it was filled for holds nothing the new one can find.
- **Each block in Solid Cache,** keyed on a digest of its subtree (its
  own JSON and its children's digests) and the fingerprint of
  `tokens.css`, rendered with Rails' collection caching through
  [blocks/_block](app/views/blocks/_block.html.erb): one `read_multi` for
  a page's sections, then one for the columns of each section it missed,
  then one for the widgets of each column it missed, and one
  `write_multi` per level for what it drew. Blocks are shared by every
  page that holds the same ones, and the header's and footer's are cached
  as a page's are, once for every page.

Every fragment key also starts with the release, so a deploy finds none
of the old fragments. The release is a digest of `app/`, `config/`,
`lib/`, `Gemfile.lock`, the schema folder's own files (its tokens,
icons and enums), the Ruby version and a key derived from the secret,
which signs library images' addresses. It names the files the process
runs, so it is computed as the process starts
([config/initializers/page_cache.rb](config/initializers/page_cache.rb)),
never at the first visit: a server whose files change before its first
page would otherwise draw the old config under the new release's name,
and keep doing so after a restart. Where code reloads (development), the
files that reload (`app/`, `lib/`, the routes and the locales, and the
schema's files) are read again whenever one of them changes, so an
edited partial or icon is never answered with a 304 for the page it no
longer draws. The schema's files count with them because the models that
read them (`SiteIcons`, `SiteTokens`, `BlockStyle`,
`BlockDocument::Schema`) reload with the code, and a change to one of
those files reloads it (`config.watchable_files`, in
[config/application.rb](config/application.rb)). The others
(`config/site.yml`, the starters of `config/parts` and the rest of
`config/`, `Gemfile.lock`) are read
once, as the process starts, and change the release only with a
restart, since a running server draws with what it read then.

| What changes | Browser | Whole page | Blocks |
| --- | --- | --- | --- |
| a publish, a restored version published, a scheduled publish | new ETag | new entry | only the changed blocks and the column and section around each |
| the site style | new ETag | new entry | all read back |
| a publish of the header or the footer, on every page | new ETag | new entry | the page's read back; the part's changed blocks drawn once for every page |
| the release | new ETag | new entry | all drawn again |

On the test page of 2 sections, 4 columns and 12 widgets
([test/integration/page_cache_test.rb](test/integration/page_cache_test.rb)):
the first visit writes 19 entries in 8 reads; the next is one read that
finds the page; one widget changed and published reads 8 keys in 4 reads,
finds 4 and writes 4 (the widget, its column, its section, the page); a
new site style reads the page and the 2 sections and writes 1; a header
published with a heading reads the page and its 2 sections, draws the
header's section, column and heading, and writes those 3 and the page,
and the next page that holds the same header finds them. The bytes
are those the partials draw with no cache at all, on the 500-block
fixture too.

Not cached: the preview (`no-store`), the 404 page and the redirects
(`no-cache`, Rails' default). No answer sets a cookie, from a drawn page,
a cached one or a 304, even to a visitor who brings cookies (a browser
sends 127.0.0.1's cookies to every port), and the layout has no CSRF
meta tag.

Production, the e2e environment and development cache in Solid Cache,
each in its own cache database (`storage/development_cache.sqlite3` for
development, which `db:prepare` makes). Development keeps Rails' switch:
caching is off until `ruby bin/rails dev:cache` turns it on, and the
browser level works there either way. The switch is read as the server
starts, so stop the server, run `ruby bin/rails dev:cache` (it says
whether caching is now enabled or disabled), and start the server again.
Rails would restart a running server itself by `tmp/restart.txt`, which
`dev:cache` touches; on Windows that restart cannot run, so
[config/puma.rb](config/puma.rb) leaves it out there, and a server left
running goes on as it was started. The tests keep the null store,
except the cache tests, which put Solid Cache in place on the tests' own
cache database (`storage/test_cache.sqlite3`) and count its calls.

From the repository root, `node tools/check-production.ts` checks this
from outside a production server: the headers, a 304, a publish seen at
the next request, and the fragments in production's Solid Cache (the
page and each of its 45 blocks after the first visit, then exactly 4 more
for one edited widget; Solid Cache's own row, an estimate of its size
that its expiry writes at random, is not one of them). In Chromium, `builder/e2e/published-cache.spec.ts` publishes
from the editor and visits from a browser with its cache on: a 200, then
a 304 over the wire, then, after an edit is published, a 200 with the new
words for the same old ETag. `builder/e2e/publish-story.spec.ts` follows
one page through all of it and counts the fragments in the run's Solid
Cache: 7 kept at the first visit (the page and its six blocks), none at
the 304, and 4 for one heading changed, whether published by hand or by a
publish set for a time. The editor's random-page agreement check
(`../builder/README.md`) compares random published pages with React, drawn,
read block by block and read whole.

## The API

[`openapi.yaml`](openapi.yaml) describes every route, request and answer
(OpenAPI 3.1). The page document is not copied there: it refers to
[`../schema/block-document.schema.json`](../schema/block-document.schema.json),
the one schema the editor and the server validate with. From the
repository root, `npm ci` then `npm run lint:openapi` lints it with Redocly
CLI 2.57.0 (with its usage data switched off); the run of 1 October found
no errors and no warnings, and planted faults (a missing `info.title`, a
reference to a missing component, a reference to a missing `$defs` inside
the schema file) each failed it.

| Route | What it does |
| --- | --- |
| `GET /api/pages`, `POST /api/pages` | the pages, and the site's header and footer apart, as `parts` (made the first time this is asked); create a page with `{title, slug}` |
| `GET /api/pages/:id`, `PATCH /api/pages/:id` | the page or part, its draft, what is live, links; set a page's next address `{slug}`, make it the home page `{home: true}` (a part takes neither: 422, keyword `part`) |
| `GET /api/pages/:id/draft`, `PUT /api/pages/:id/draft` | read; save `{revision, document, saveId}` |
| `POST /api/pages/:id/publish` | publish the draft, optionally only at `{revision}` |
| `GET /api/pages/:id/schedules`, `POST ...` | the page's scheduled publishes, newest first; schedule the draft at `{revision}` for `{at}` (ISO 8601, UTC) |
| `POST /api/pages/:id/schedules/:schedule_id/cancel` | cancel a pending one, or 409 `not_pending` saying what became of it |
| `GET /api/pages/:id/versions`, `POST ...` | list; "Save version" `{name?}` |
| `GET /api/pages/:id/versions/:number`, `POST .../restore` | read one; restore it into the draft |
| `GET /api/pages/:id/responses?form=&before=` | what visitors sent with the page's forms, newest first, 50 at a time, each with an excerpt; `next` continues it; a count per form |
| `GET /api/pages/:id/responses/:response_id`, `DELETE ...` | one response whole, with its version and its form's fields as they were; delete it for good |
| `POST /api/media/direct_uploads` | start an image upload (Active Storage's request and answer) |
| `GET /api/media`, `POST /api/media` | list; create from `{signedBlobId, width, height, alt?}` |
| `PATCH /api/media/:id`, `DELETE /api/media/:id` | change the proposed alt text; delete, or 409 with who uses it |
| `GET /api/site-style`, `PUT /api/site-style` | the palette, type scale and letter width, with their curated values; replace them (the letter width when given) |
| `GET /api/site` | the site's settings: its time zone |

**Errors** have one shape, `{"error": <code>, "message": <sentence>}`. A
422 adds `errors`, each with a JSON `pointer` into the request body, the
`keyword` of the rule broken, and the `blockPointer` of the block that
holds the value, so the editor can mark it. A body with a member name
repeated in one object gets 422 `duplicate_key` with its `pointer`; a body
that is not JSON or not UTF-8 gets 400 `malformed_json`. A string member
holding U+0000 gets 422 with keyword `pattern` at its pointer, a media id
in the path that is not in the form of one gets 404, and so does any other
address or method under `/api/`. A failure nothing foresaw is logged and
answered 500 `internal_error`, in the same shape: the API never answers
with an HTML page.

U+0000 is refused before any query because SQLite stops reading a
statement's text at it. Development turns prepared statements off for its
query log tags, so values travel inside the SQL text, and a slug, a file
name, a checksum or a media id holding one failed there with an HTML 500.
[test/integration/api/unexpected_input_test.rb](test/integration/api/unexpected_input_test.rb)
sends each of them the way development does; with the refusal taken out,
the slug of a new page, the next address and the upload got a 500, the
media id a 500 instead of a 404, and an alt text was refused by the model
under another keyword. With the catch-all handler taken out, a planted
failure reached the test as an exception instead of the JSON 500.

**Writes from other sites.** Listening on 127.0.0.1 keeps other machines
out, but not other sites: a page from anywhere, open in a browser on this
machine, can send requests that need no CORS preflight (a form POST, or a
fetch with mode `no-cors` and a `text/plain` body), and the browser
delivers them. Before this rule such a page could create pages, publish a
draft nobody had reviewed, save and restore versions and start uploads.
So every write is refused with 403 `forbidden_origin` when the browser
says it comes from another site (`Sec-Fetch-Site: cross-site` or
`same-site`) or names another origin (`Origin`), and every POST, PUT and
PATCH with 415 `unsupported_media_type` unless it is sent as
`application/json`, which a browser cannot do towards another origin
without a preflight the API never grants. curl and the repository's tools
send no `Origin`, and pass. In production `config.hosts` lets only
`127.0.0.1`, `localhost` and `[::1]` in, so a domain made to resolve to
127.0.0.1 (DNS rebinding) cannot pass for the CMS's own origin; development
has Rails' own list, which refuses such a name too.
[test/integration/api/other_sites_test.rb](test/integration/api/other_sites_test.rb)
sends the text/plain create, the empty form post that publishes, and JSON
from a foreign origin: with the rule taken out, five of its seven tests
failed, the page created and the draft published. The editor reaches the
API through its development server's proxy, which keeps the Host the
browser asked for, so its origin is the one addressed: a test saves a
draft and starts an upload with `Host: 127.0.0.1:4900` and that origin,
and gets the upload address on that host. With the Host planted as the
CMS's own, 127.0.0.1:3900, the save got 403. The editor's
`../builder/e2e/probe.spec.ts` does the same from Chromium through the
real proxy.

**Saving.** The revision check is one statement,
`UPDATE drafts SET ..., revision = revision + 1 WHERE page_id = ? AND revision = ?`,
and the rows it changed decide. A 409 gives `currentRevision` and
`lastSaveId`, the id of the save that got there. A retry of the last
accepted save, the same `saveId`, `revision` and document, is answered
200, so a save whose answer was lost never comes back as a false
conflict; the same `saveId` with another document or another revision is
a 409, so a second tab that numbers its saves the same way is never told
that text the server dropped was saved.

**Versions** are kept on publish, on restore, on "Save version", on
scheduling a publish, and at most every ten minutes while someone saves;
the automatic ones are pruned every night (see "The jobs"). A restore first keeps the
draft it is about to replace as a `before-restore` version (unless the
draft is exactly the newest version already), so the edits made since the
last automatic version are never lost to it; the answer names that
version as `kept`. Restoring copies a version
back into the draft after upgrading it to the current `schemaVersion`
([app/models/block_document/upgrade.rb](app/models/block_document/upgrade.rb),
where the steps will go when the schema changes; version 1 is the first).

**Publishing** makes a `publish` version, points the page at it, moves
`publishedAt` forward and never back, and applies the draft's address; the
old one becomes a redirect to the page. `api`, `up`, `assets`, `rails`,
`preview` and any name a file in `public/` answers (such as `404`) are
refused as addresses. What is live names the draft revision it was taken
from, `published.draftRevision`: the draft's revision minus it is the
number of saves visitors do not see yet, the editor's "N changes not
live".

**Scheduled publishing.** `POST /api/pages/:id/schedules` with
`{revision, at}` keeps the draft at that revision as a version of kind
`scheduled` and publishes that version at `at`, whatever the draft holds
by then: edits made in between wait for the next publish. `revision` is
the one the person scheduling has seen (409 if the draft moved on, as for
a publish); `at` is ISO 8601 in UTC with `Z`, later than now and at most a
year ahead (422 at `/at`, and February 30 or 24:00 are refused rather than
rolled over); a revision already live is refused at `/revision`. A page
has at most one pending schedule: a new one replaces it, and the answer
names it as `replaced`. The page's own answers carry the pending one as
`scheduled`. A publish by hand settles it as `superseded`: it put that
revision, or a later one, live. The address applied is the draft's at the
time of the publish, as for any publish. The site's time zone is written
in [config/site.yml](config/site.yml) (`time_zone: Europe/London`), set as
`config.time_zone` and given by `GET /api/site` as `timeZone`; the editor
shows and takes times in it, and the API keeps UTC.

**Media.** JPEG, PNG, WebP and GIF, never SVG, at most 10 MB, recognised
by their first bytes. The upload goes to `/api/media/direct_uploads`, not
to Active Storage's own endpoint, which wants a CSRF token the editor does
not have (a test shows the stock one refusing with forgery protection on,
and this one accepting). Every save indexes the images a draft or version
uses, so a delete can answer 409 with them; an image nothing has named
for 30 days is purged by a job (see "The jobs"). An item's `url` is Active
Storage's proxy route, the address the published page gives the image
too: a path on this site, answered with the bytes, cacheable for good.

**Site style.** The tone of each palette slot and the type-scale choice,
only from `site-tones` and `site-type-scale` in
[`../schema/tokens.json`](../schema/tokens.json), or, for a slot, a
colour of the site's own written `#rrggbb` (anything else is refused at
`/palette/<slot>`, "must be one of …, or a colour as #rrggbb").

**Classes, anchors and a sticky header.** Every block may name CSS
classes of the site's own (`className`, "hero big") and an anchor
(`anchor`): `block_root` writes the classes after the theme's and the
anchor as the element's id, through `RenderPolicy.classes` and
`RenderPolicy.anchor`. Anchors are unique on the page (`uniqueAnchor`)
and a class may not be one of the theme's (`reservedClass`, both rules
of `lib/block_document/rules.rb`). A header whose document says
`"sticky": true` is drawn with `data-sticky`, and `site.css` keeps it
at the top of the window. The attribute holds the header's rows on a
desktop, a tablet and a phone (`RenderPolicy.sticky_rows`: one for each
section, one for each column where its columns stack), and the page's
anchors stop that many rows below the window's top: the page has no
script to measure the header.

**Custom CSS** (`app/models/custom_css.rb`). The site style holds the
site's own stylesheet, `custom_css` (`customCss` in the API, "" for
none). `CustomCss.check` refuses what would not keep to the site, as the
editor's `custom-css.ts` does on the shared cases of
`../contract/custom-css/`: a rule left open, a `}` that closes nothing,
an `@import`, an address with a brace outside quotes, more than 50 000
characters; the 422 is at `/customCss`, with the line. The layout links
`/custom.css?v=<digest>` after the free colours when there is some:
`CustomCssController` serves it inside `@scope (.site) { … }`, kept for
good when the address names the stylesheet as it is now, unkept for an
older one. The site style's key of the page cache holds it, so a change
redraws every page once.

**Free colours** (`app/models/free_colors.rb`). A slot or a block's
background or colour may name a colour of its own (the schema's
`freeColor`). The page carries it as a data attribute, never an inline
style, which the pages' `style-src 'self'` would block: `data-primary`
on `.site` for a slot, `data-bg`, `data-fg` or `data-line` (and
their `tablet-` and `phone-` forms) on a block. The layout links
`/colors/<digest>.css` after `tokens.css` when the page, its header or
its footer names one. Its rules come from the site's Text and Background
tones, its free tones by slot and the free colours its blocks name (a free
background takes the site tone that reads better on it, as a slot's band
does); they are written as the page is drawn and kept once under their
SHA-256 (`ColorSheet`, the `color_sheets` table), so the address names
only rules a page was drawn with, however many colours it names.
`FreeColorsController` serves them with `Cache-Control: public,
max-age=31536000, immutable`; an address no page links is a 404. On one
device a block's own colour wins over the one its background brings, as
with the curated tones, and a tablet's or a phone's own background brings
its colour over the desktop's own colour. The editor
writes the same bytes for its canvas (`builder/src/render/free-colors-css.ts`):
`test/models/free_colors_test.rb` and the editor's
`free-colors.contract.test.ts` hold both to `../contract/free-colors/`. The choice reaches the
page as `data-type-scale` on `.site`, and `tokens.css` sizes every step of
Gentle and Strong under that attribute (Balanced, the default, is the
plain `.sw`). From the repository root, with the server running,
`node tools/type-scales.ts http://127.0.0.1:3900` sets each choice
through the API in turn, reads the computed font sizes of the home
page's headings in headless Chromium at 1280, 768 and 390 wide, and puts
the style back. On 1 October 2026 (Gentle / Balanced / Strong, px):

```

 390 wide: display 28.0 / 40.0 / 48.0;  heading-2 22.0 / 28.0 / 31.0;  heading-3 20.0 / 23.0 / 25.0
```

With Gentle's rules renamed away in `tokens.css`, it failed on every
step and width, Gentle drawing Balanced's sizes.

The letter width is how wide the Headings typeface, Archivo, is drawn:
Narrow, Normal, Wide or Widest, from `site-letter-width`, Normal for a
new site. Each choice gives three widths of Archivo's width axis, custom
properties of `tokens.css` on the attribute `data-letter-width`: one
for headings, the logo and an icon box's title, one for buttons and an
accordion's question, one for a form's labels and a quote's caption. A
menu keeps its own width, 110%, the one its letters are measured at for
its fold (`schema/header-metrics.json`), so a change of width moves no
fold. `PUT /api/site-style` takes `letterWidth` when it is given and
keeps the style's own when it is not; a style kept before the choice
existed took Normal. A change of it alone is a new page for every
browser, as a tone's is.

**Header and footer.** The site's parts are pages of their own kind
(`kind`: `header` or `footer`, at most one of each), read, saved,
versioned, scheduled and published by a page's own routes, by their ids;
`GET /api/pages` lists them apart, as `parts`, the header then the
footer, and makes them the first time it is asked, each with its starter
as its draft. A part has no address and is never the home page: a
`PATCH` that names either is a 422 at its member, keyword `part`. Its
draft is held to a page's rules and to two of its own, no form and no
anchor on any block (it is drawn in every page, beside the page's own
blocks, whose anchors its own are not checked against), refused at the
form's block or at the anchor with the keyword `part`: at each save, and
again, as a page's rules are, when a publish, a schedule, a version or a
restore reads a stored document. The site's time zone is not a part's:
only `config/site.yml` sets it.

**Responses.** What visitors sent with a page's forms (see "Forms a
visitor sends") is read and deleted under the page, and only there: a
response asked for under another page is 404. The list is newest first,
50 at a time; `next` is the `before` that continues it, `null` at its
end, and `form` keeps one form's. `forms` counts each form of the page
that has responses, whatever the query, so the editor offers only those.
Each item has an excerpt, the first text answer with more than white
space, on one line and cut at 120 characters as a reader counts them
(grapheme clusters), saying whether it was cut. A response read whole
has the number of the published version it came from, the form's fields
as that version had them and every field's answer by name. Deleting one
is for good, as a visitor may ask; the page and its versions stay. The
query is read from the address itself, so a parameter named twice or
written as `form[]` is 400 `invalid_query` with its name, rather than
read as its last value or as a list. Rails 8.1 stopped escaping `<`, `>`
and `&` in JSON answers; these answers, the only ones carrying what
strangers wrote, ask for it, so the body holds no markup even if
something reads it as HTML, and the strings are the same once parsed.
Every answer here, errors included, is `Cache-Control: no-store`: what
visitors sent is personal data, and Rails' default for the rest of the
API (`max-age=0, private, must-revalidate`) still lets the browser keep
a copy.
[test/integration/api/responses_test.rb](test/integration/api/responses_test.rb)
plants each fault and sees it fail: the escaping left out, the origin
check skipped for the delete, the query read without its checks, a
response found by id outside its page, the list oldest first, `next`
never given, the counts following the query, and the version read from
what is live now.

## The jobs

Solid Queue, on a SQLite database of its own (`queue`), no Redis. Its
supervisor runs inside Puma ([config/puma.rb](config/puma.rb)) in
development and in e2e, and anywhere `SOLID_QUEUE_IN_PUMA` is set; a
production run without it runs `ruby bin/jobs` beside the server, or no
job at all. On Windows, which cannot fork, the supervisor and its workers
are threads of Puma's own process (`solid_queue_mode :async`); on Linux
and macOS a child process (`:fork`). `bin/jobs` does the same: on Windows
it takes Solid Queue's `async` mode unless `--mode` or
`SOLID_QUEUE_SUPERVISOR_MODE` says another (Solid Queue's own default,
`fork`, stopped it there with `fork() function is unimplemented on this
machine`). [test/bin/jobs_test.rb](test/bin/jobs_test.rb) starts it for
real on databases of its own and sees its supervisor, dispatcher, worker
and scheduler registered and the process staying up, and
`node tools/check-production.ts` runs it beside a production server and
sees a page scheduled for 15 seconds ahead not live before and live after
(1.9 seconds late on 4 October 2026). Development keeps its queue in
`storage/development_queue.sqlite3`, which `db:prepare` makes.

- **PublishPageJob** is enqueued for a schedule's time and carries only
  its id. When it runs it looks again ([app/models/scheduled_publication.rb](app/models/scheduled_publication.rb),
  `run!`): cancelled, replaced, already run or superseded, it does
  nothing and says so in one log line (`scheduled publish 12 of page 3:
  cancelled at 2026-10-04T10:00:00Z, nothing to do`); run before its time,
  it sets itself again for it; otherwise it puts the scheduled version
  live as a new `publish` version, through the same method a publish by
  hand uses, so the caches keyed on the published version follow. If the
  pages database is busy past SQLite's 5 second timeout at that moment
  (`ActiveRecord::StatementTimeout`; a pool with no free connection, or a
  deadlock, are the same), the job waits 10 seconds and tries again, up to
  12 times; it is safe to run again, since each run looks again at what
  it finds.
- **EnqueueOverdueSchedulesJob**, every minute: a schedule still pending
  more than a minute after its time, whose job was lost or failed for
  good after those tries, gets its job again
  (`ScheduledPublication.sweep_overdue!`). A schedule set going again is
  left alone for the next five minutes (its `updated_at` is when), so one
  that fails every time is tried every five minutes, not every minute.
  The editor says meanwhile that it "should have gone live" at its time,
  and goes on reading the page every half minute until it has. A job that
  failed for good stays in Solid Queue's `solid_queue_failed_executions`
  with its error, which Solid Queue itself never clears: while its
  schedule waits it says why the page is late. Once the schedule is
  settled (put live by the job the sweep set going, or published,
  cancelled or replaced by a person) or gone, the sweep discards that
  failed job (`ScheduledPublication.discard_settled_failures!`), so no
  failure is kept for a publish that has happened.
  [test/jobs/failed_publishes_test.rb](test/jobs/failed_publishes_test.rb)
  plants such failures on Solid Queue's real tables, in the e2e
  environment, and sees those of settled schedules go with their jobs,
  and a waiting schedule's failure, another job's and the jobs still
  coming at their time stay.
- **PruneVersionsJob**, every night at 3:30 by the site's clock
  ([config/recurring.yml](config/recurring.yml)), deletes automatic
  versions only: of each page's, the newest 50 stay, and beyond them those
  made in the last 30 days (days of 24 hours, counted in UTC). Published,
  scheduled, manual, restore and before-restore versions always stay, and
  so does any version a page serves or a schedule names.
- **PurgeMediaJob**, at 4:00, deletes with its file a library image that
  no draft and no kept version names, and none has named for more than 30
  days (each save and each new version records when it last named one);
  an image never placed on a page stays, since a person put it in the
  library on purpose. It also deletes an upload that never became a
  library image, after two days.

The jobs read the time when they run, so the tests set it with
`travel_to` and run the queue's work with `perform_enqueued_jobs(at:
Time.current)`, never the forms that run future jobs at once
([test/integration/api/schedules_test.rb](test/integration/api/schedules_test.rb),
[test/jobs/](test/jobs)).

**A hard stop.** Windows stops a console server without a word (a closed
window, `taskkill /F`, a test harness's tree kill), and Solid Queue's rows
stay: its processes, and the jobs a dead worker held. Solid Queue itself
would find those processes only once their heartbeat is five minutes old,
and then mark their jobs failed for good. So as a supervisor starts, and
before its workers take a job, [lib/queue_orphans.rb](lib/queue_orphans.rb)
deregisters every row of this machine whose process is gone (or whose
process id the new server was given), which puts their jobs back in the
queue; every job here may run twice, since each looks again when it runs.
[test/lib/queue_orphans_test.rb](test/lib/queue_orphans_test.rb) plants
such rows on Solid Queue's real tables, in the e2e environment, and sees
the held job back in the queue and a live process's row left alone. On
4 October 2026 an e2e server on 127.0.0.1:3905, with a publish scheduled
20 seconds ahead, was stopped with `taskkill /T /F` and started again
after that time; the restart logged

```
Solid Queue: released 4 row(s) of a server that stopped abruptly (Supervisor(async) 13196, Dispatcher 13196, Worker 13196, Scheduler 13196); their jobs are back in the queue
```

and the overdue publish went live within the second the server was up.
A publish whose time passes while no server runs happens at the next
start. Then every pending schedule whose time has passed gets its job
again (`ScheduledPublication.enqueue_overdue!`): a job that never reached
the queue, or that Solid Queue marked failed for good, would otherwise
leave its schedule pending forever; a job that was still coming runs too,
and finds the schedule settled. While the server runs, the minute-by-minute
sweep above does the same for a schedule that is more than a minute late.

## The e2e environment

The CMS the editor's tests start for themselves
([../builder/e2e/harness/servers.ts](../builder/e2e/harness/servers.ts)),
on port 3901: [config/environments/e2e.rb](config/environments/e2e.rb).
It behaves as production does where that matters to them: forgery
protection on, eager loading, `solid_cache` and `solid_queue` (the queue
run inside Puma, so a scheduled publish really happens while a test
watches), only `127.0.0.1`, `localhost` and `[::1]` as host names, and
the forms' count in Solid Cache. The tests reach it from `127.0.0.1`,
and this environment alone counts the forms under the address
`X-Forwarded-For` names (`config.x.submission_limit_by`, set in
`e2e.rb`), so each test's forms are counted under an address of its own;
any other environment counts under the socket's peer. Its data is its own:
three databases, primary, cache and queue, and an Active Storage root. The
harness gives each run a folder under `tmp/`, passes the paths as
`DATABASE_URL`, `CACHE_DATABASE_URL`, `QUEUE_DATABASE_URL` and
`CMS_STORAGE_ROOT`, and deletes the folder once the server is stopped;
without them the paths default to `tmp/e2e/`. Like production, it reads its
secret from the environment. By hand, in a POSIX shell:

```
RAILS_ENV=e2e SECRET_KEY_BASE_DUMMY=1 ruby bin/rails db:create db:schema:load
RAILS_ENV=e2e SECRET_KEY_BASE_DUMMY=1 ruby bin/rails server -p 3901
```

Run on 2 October 2026, the first made the three databases in `tmp/e2e/`,
the second answered 200 on `/up` and `{"pages":[]}` on `/api/pages`;
`tmp/e2e/` is deleted by hand afterwards, with the server stopped.

## Production

No credentials file is committed. Production reads its secret from the
`SECRET_KEY_BASE` environment variable and does not boot without it; for a
local run with nothing to protect, `SECRET_KEY_BASE_DUMMY=1` uses a
throwaway one. The databases are SQLite files in `storage/`, and the
uploaded pictures are under `storage/` too; `DATABASE_URL`,
`CACHE_DATABASE_URL`, `QUEUE_DATABASE_URL` and `CMS_STORAGE_ROOT` move
them, as the e2e environment's do, which is how `tools/measure-server.ts`
runs a production server on files of its own and deletes them.

Production forces SSL and assumes a proxy in front that ends it;
`CMS_FORCE_SSL=0` turns both off for a local run over plain HTTP, where
Strict-Transport-Security would pin 127.0.0.1 to HTTPS in the browser.
The fingerprinted files under `/assets` are served with
`public, max-age=31536000, immutable` by a `Rack::Static` rule scoped to
`/assets`, with `cascade: true`, so a file that does not exist is the app's
404 without that header.
